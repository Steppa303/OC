## 2. UI‑Komponente: “Buch‑Render‑Dashboard”

### 2.1 Layout

```
+---------------------------------------------------------------+
| Buch: [Scheibenwelt 08] • Wachen! Wachen! (13 Kap.)           |
+---------------------------------------------------------------+
| Gesamt:  ⏳ 0 %  | ETA: ––  | Größe: 0 MB                     |
+---------------------------------------------------------------+
| Kapitel | Status      | Fortschritt | ETA  | Größe (Δ)       |
|---------------------------------------------------------------|
| 0      | completed   | 100 %       | 00:01| 0.3 MB (File)   |
| 1      | completed   | 100 %       | 00:02| 0.8 MB          |
| 2      | processing  |  42 %       | 00:30| 3.4 MB (partial)|
| 3      | pending     |   0 %       | ––  | ––              |
| …                                                          |
| 12     | pending     |   0 %       | ––  | ––              |
+---------------------------------------------------------------+
| [Start All] [Pause] [Cancel] [Refresh]                        |
+---------------------------------------------------------------+
```

- **Gesamt‑Zeile** zeigt aggregierten Fortschritt, geschätzte Restzeit (Summe aller `ETA`s) und aktuelle erwartete Dateigröße (kleiner‑bis‑groß‑Schätzwert, siehe unten).
- **Kapitel‑Zeile** ist eine kleine Fortschritts‑Bar + Prozent‑Anzeige. Klick‑bar → öffnet ein Modal mit **Live‑Preview** (falls `output_path` existiert, wird die partielle WAV sofort abgespielt) und Detail‑Log (letzte 5 `PROGRESS:`‑Zeilen).

### 2.2 Berechnungen

| Kennzahl | Formel (Backend) |
|----------|------------------|
| **Kapitel‑ETA** | `duration_est = (text_len / 20) s` (20 Zeichen ≈ 1 Sekunde). <br> `remaining = (100 - progress) / 100 * duration_est` |
| **Gesamt‑ETA** | Summe aller `remaining`‑Werte (nur `processing` + `pending`). |
| **Groß‑Schätzung** | `size_est = duration_est * 384 kbps / 8 ≈ bytes`. <br> Für das Buch: Σ über alle Kapitel. |
| **Δ‑Größe (partial)** | Wenn `output_path` existiert, `filesize(output_path)` – `size_est * (progress/100)` gibt an, wie viel bereits geschrieben ist. |

> **Why 20 Chars ≈ 1 s?** Das ist die gerundete Lesegeschwindigkeit von XTTS DE (≈ 120 WPM). Wenn du genauer willst, misst du das beim ersten Kapitel und übernimmst den Faktor.

## 3. Technische Umsetzung

1. **WebSocket / SSE** – Deine `tts‑queue‑service.js` sendet nach jedem `PROGRESS`‑Update eine Nachricht an den Front‑End‑Server (z. B. über `socket.io`).  
   Payload: `{jobId, chapter, progress, status, outputPath}`.

2. **Polling‑Fallback** – Falls kein WebSocket, setze einen kurzen (30 s) Poll‑Job, der `SELECT … FROM tts_queue WHERE book_id = ?` ausführt. Das ist cheap, weil `progress`‐Updates nur bei Änderungen geschrieben werden.

3. **Partial‑WAV‑Streaming** – Sobald `output_path` existiert, liefert das Front‑End die Datei via HTTP Range‑Requests, sodass du schon die ersten Sekunden hörst, während das Kapitel noch rendert. (Dein `write_partial_wav` erzeugt atomare Writes, das funktioniert bereits.)

4. **Cancel‑/Pause‑Button** – Ein Klick ruft `POST /api/tts/queue/:id/cancel` (oder ein DB‑Update + `kill` des zugehörigen PID) auf. Der Front‑End ändert den Status sofort zu `cancelled`, sodass die UI nicht „hängt“.

5. **Refresh‑Button** – Falls du das WebSocket‑Band‑breite‑Problem vermeiden willst, kann ein manueller Refresh die gesamte Queue neu laden (nur einmal beim Öffnen nötig).

## 4. Was du jetzt im UI sehen würdest

- **Sobald das Modell geladen ist**, ändert sich der Status von `pending → processing` und die Fortschritts‑Bar springt von 0 % auf 1 % (oder bleibt kurz bei 0 % – der erste `PROGRESS`‑Eintrag kommt erst nach dem ersten Satz).
- **Nach den ersten 5 Sätzen** (ca. 20 s) wird die partielle WAV geschrieben → das Modal zeigt sofort einen **Play‑Button**. Das gibt dir sofort Feedback, dass das neue „Leser M“-Stimme‑Referenz tatsächlich verwendet wird.
- **Während das Kapitel weiter rendert**, wächst die Prozent‑Anzeige und die geschätzte Restzeit schrumpft (z. B. von 70 Min auf 65 Min → 60 Min …). Sobald `progress == 100`, wechselt `status` zu `completed` und das endgültige File wird gelistet.

## 6. Warum das elegant ist

- **Keine manuelle Log‑Durchforstung** – alles ist in einer Tabelle zusammengefasst.
- **Live‑Preview** gibt sofort ein Ohr‑Feedback, kein Warten bis das ganze Kapitel fertig ist.
- **Aggregierte Kennzahlen** (Gesamt‑ETA, Gesamt‑Größe) helfen dir, deinen Tag zu planen (z. B. „ich starte das Rendering am Abend, krieg 2 h Morgen fertig“).
