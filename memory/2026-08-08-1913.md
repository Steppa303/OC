**🔴 Problem 1: WebMIDI fragt nicht nach Permission**

Root Cause ist lächerlich simpel: `MidiEngine.init()` wird **ausschließlich** in `SettingsPanel.jsx` aufgerufen — und das nur, wenn der User das Panel manuell öffnet. `App.jsx` hat keinen `useEffect` der das beim Mount macht. Browser-Permission-Prompt kommt also nie, wenn der User nicht zufällig aufs Settings-Icon klickt.

Fix: `useEffect` in `App.jsx` der `midiEngine.init()` sofort nach Mount aufruft. Falls der Browser ne User-Gesture braucht → "Connect MIDI" Button im Header statt totem "No Device" Badge.

**Betroffene Dateien:** `App.jsx`, `Header.jsx`, `SettingsPanel.jsx` (Redundanz raus).

---

**🔴 Problem 2: External Clock Sync via Web MIDI**

Aktuell gibt's **null** MIDI-Input-Logik. Kein einziger Event-Listener für eingehende MIDI-Messages. `MidiEngine.js` kann nur Output. Für Clock-Sync muss:

1. **`MidiClockParser.js` (NEU)** — Parst System-Realtime-Messages (0xF8 Clock, 0xFA Start, 0xFB Continue, 0xFC Stop), berechnet BPM aus Clock-Intervallen (24 PPQN), feuert alle 6 Clocks nen Step-Trigger.

2. **`MidiEngine.js`** — Input-Ports enumerieren, `onMIDIMessage` Event-Handler, `selectInputDevice()`, Clock-Messages an Parser routen.

3. **`MidiScheduler.js`** — Dual-Mode: `clockSource: 'internal'|'midi'`. Im External-Mode wird nicht per `setTimeout` gescheduled, sondern jeder Clock-Puls feuert direkt den nächsten Step. Timing kommt vom Master, kein eigener Timer.

4. **`useStore.js`** — Neue Felder: `clockSource`, `midiInputDevices`, `externalBpm`, `isExternalRunning`.

5. **UI:** Settings kriegt Clock-Source-Toggle (Internal/MIDI) + Input-Device-Select. TransportBar zeigt "EXT" Badge mit ermitteltem BPM (read-only), Play/Stop werden disabled im External-Mode.

**Geschätzter Aufwand:** ~5-6h. Alles isoliert zum Engine-Core — Pattern-Generierung, Genre-Templates etc. bleiben unangetastet.
