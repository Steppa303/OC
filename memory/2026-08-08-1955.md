## 📋 Umsetzungsplan: BeatGen Echtzeit & MIDI I/O

**Gespeichert in:** `projects/beatgen/PLAN_REALTIME_FIXES.md`

---

### 1️⃣ MIDI-Device in beiden Listen finden

**Problem:** Output- und Input-Ports sind komplett getrennte Dropdowns. Wenn du z.B. deine TR-8S als Output wählst, musst du sie im Input-Dropdown nochmal manuell suchen.

**Fix:**
- `MidiEngine.js` → neue `matchInputForOutput(deviceId)` Methode (Name-Matching)
- `SettingsPanel.jsx` → "🔗 Use same device for input" Button neben dem Input-Select
- Input-Select wird **immer** sichtbar (nicht nur bei `clockSource=midi`), weil Transport-Befehle auch im Internal-Mode relevant sind

**Aufwand:** Klein — eine Methode + ein Button + Label-Change

---

### 2️⃣ Änderungen in Echtzeit wirksam (kein Play/Stop nötig)

**Problem:** Jede Parameter-Änderung (Genre, Mood, Swing) setzt nur `patternDirty = true`, aber das neue Pattern wird erst am **Takt-Ende** (nach 16 Steps) angewendet. Fühlt sich an wie Lag.

**Fix:**
- `MidiScheduler.js` → neue `loadPatternLive(pattern, tracks)` Methode — überschreibt das aktive Pattern **sofort**, der Scheduler-Lookahead (100ms) pickt die neuen Steps beim nächsten Scheduling-Zyklus auf
- `App.jsx` → neuer `useEffect` auf Genre/Mood/Swing/Tracks — bei jeder Änderung sofort Pattern neu generieren und via `loadPatternLive()` laden
- Kein `markDirty()` mehr nötig im Internal-Mode (Bar-End-Regeneration nur noch für External-Clock-Mode)
- 50ms Debounce damit nicht bei jedem Slider-Pixel das Pattern neu generiert wird

**Aufwand:** Mittel — Scheduler-Erweiterung + neuer Effect + Debounce

---

### 3️⃣ Externe MIDI Start/Stop/Continue immer beachten

**Problem:** Wenn ein externes Gerät (z.B. TR-8S) Start/Stop sendet, wird das nur im `clockSource=midi` Mode beachtet. Im Internal-Mode ignoriert die App das komplett.

**Fix:**
- `App.jsx` → `clockParser.onStart/onStop/onContinue` Callbacks checken **nicht mehr** auf `clockSource === 'midi'`
- Bei `onStart`: Pattern generieren, Scheduler starten (mit internal ODER external clock, je nach Mode)
- Bei `onStop`: Scheduler stoppen, Store auf `isPlaying: false`
- Bei `onContinue`: Wie Start verhalten
- `TransportBar.jsx`/`Header.jsx` → Play-Button disablen wenn externer Transport aktiv (Konflikt-Vermeidung: User klickt Play während Master schon läuft)
- `useStore.js` → neuer `externalTransportActive` State für UI-Indikator

**Aufwand:** Mittel — Callback-Logik umbauen + UI-State

---

### 🔄 Reihenfolge

1. **Fix 1** (MIDI-Linking) — isoliert, unabhängig
2. **Fix 2** (Echtzeit-Pattern) — isoliert, braucht nur Scheduler + App
3. **Fix 3** (Externer Transport) — baut auf Fix 2 auf (braucht `loadPatternLive`)

### ⚠️ Risiken

- **Live-Pattern-Load:** Theoretisch Timing-Glitch wenn Pattern mitten im Step wechselt → Mitigation: Pattern nur beim nächsten Step-Übergang aktivieren, aktive Noten nicht killen
- **Performance:** Pattern-Regeneration bei jedem Slider-Move → 50ms Debounce
- **Device-Matching:** Zu aggressives Name-Matching → nur Substring-Match mit ≥3 Zeichen
